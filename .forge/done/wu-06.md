# Add Caddy bootstrap and management

## Outcome

Running `herald caddy start` starts a caddy-docker-proxy container that automatically discovers Docker containers with Caddy labels and provisions TLS certificates via Let's Encrypt. Running `herald caddy stop` stops it. Running `herald caddy status` shows whether Caddy is running and lists the active domains. After this WU, apps deployed by herald (wu-05) are automatically accessible on their configured domains with HTTPS.

## Values

1. Zero-touch TLS — Caddy must auto-provision certificates. No manual cert management.
2. Reliability — Caddy must survive server reboots (restart policy: always) and recover from crashes.
3. Non-destructive — starting Caddy must not affect already-running containers. Stopping Caddy only stops the proxy, not the apps.

## Context

- `internal/deployer/deployer.go` — generates compose override files with Caddy labels on app containers:
  ```yaml
  labels:
    caddy: "budget.example.com"
    caddy.reverse_proxy: "{{upstreams 3000}}"
  ```
  These labels are what caddy-docker-proxy reads to configure routing.
- `internal/config/config.go` — `Config.Server.DeployDomain` is the domain where herald's webhook endpoint is exposed. Caddy should also route this domain to herald's HTTP server.
- caddy-docker-proxy (https://github.com/lucaslorentz/caddy-docker-proxy) is a Caddy plugin that auto-configures Caddy from Docker container labels. It watches the Docker socket for container start/stop events and updates Caddy's config dynamically.
- All app containers and Caddy must share a Docker network named `caddy`. This network is external (not managed by any single compose project).

## Creates

- `internal/caddy/caddy.go` — Caddy lifecycle management: start, stop, status.
- `internal/caddy/caddy_test.go` — unit tests for generated compose content.
- `cmd/caddy.go` — `herald caddy` command with `start`, `stop`, `status` subcommands.

## Modifies

- `cmd/root.go` — add `caddy` to the list of available commands in help text.
- `internal/deployer/deployer.go` — ensure the `caddy` Docker network exists before deploying apps. Add network creation as a pre-deploy step.

## Requirements

### 1. Caddy Docker network

Before starting Caddy or deploying any app, ensure a Docker network named `caddy` exists:

```sh
docker network inspect caddy >/dev/null 2>&1 || docker network create caddy
```

This is an external network shared by Caddy and all app containers.

### 2. Caddy compose file

Herald generates and manages a compose file for Caddy at `<stacks_dir>/caddy/compose.yml`:

```yaml
services:
  caddy:
    image: lucaslorentz/caddy-docker-proxy:2.9
    container_name: herald-caddy
    restart: always
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"   # HTTP/3
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - caddy_data:/data
      - caddy_config:/config
    environment:
      - CADDY_INGRESS_NETWORKS=caddy
    networks:
      - caddy
    labels:
      caddy.email: "${acme_email}"

volumes:
  caddy_data:
  caddy_config:

networks:
  caddy:
    external: true
```

The `acme_email` is derived from the config. Add an `acme_email` field to the `Server` config struct (required). Default to `webmaster@<deploy_domain>` if not set.

### 3. Herald's own Caddy labels

Herald's webhook server needs to be accessible via the `deploy_domain`. Since herald runs as a systemd service (not a Docker container), Caddy can't discover it via labels. Instead, herald must configure Caddy to reverse-proxy to itself.

Create a sidecar container that exists solely to carry Caddy labels for herald:

```yaml
  herald-proxy:
    image: alpine:3
    container_name: herald-proxy-label
    restart: always
    command: ["sleep", "infinity"]
    networks:
      - caddy
    labels:
      caddy: "${deploy_domain}"
      caddy.reverse_proxy: "{{upstreams}}"
      caddy.reverse_proxy.to: "host.docker.internal:${herald_port}"
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

This allows Caddy to route `deploy.example.com` to herald's HTTP server running on the host.

### 4. Start command

`herald caddy start`:
1. Ensure the `caddy` network exists.
2. Write the Caddy compose file to `<stacks_dir>/caddy/compose.yml`.
3. Run `docker compose -f <path> -p herald-caddy up -d`.
4. Wait up to 30 seconds for the Caddy container to be healthy.
5. Print: `caddy started on :80/:443, ACME email: <email>`.

### 5. Stop command

`herald caddy stop`:
1. Run `docker compose -f <path> -p herald-caddy down`.
2. Print: `caddy stopped`.
3. Do NOT remove the `caddy` network or volumes (certificates are in `caddy_data`).

### 6. Status command

`herald caddy status`:
1. Check if the `herald-caddy` container is running.
2. If running, query the Docker API (via `docker inspect`) for the container's health status and uptime.
3. List all containers on the `caddy` network that have `caddy` labels (these are the proxied services).
4. Print:

```
Caddy: running (up 3 days)
ACME email: webmaster@example.com

Proxied domains:
  budget.example.com         → herald-budget-app:3000
  tracker.example.com         → herald-tracker-app:3000
  cloud.example.com            → herald-nextcloud-web:80
  deploy.example.com         → host:8080 (herald)
```

### 7. Caddy management struct

```go
type CaddyManager struct {
    Config   *config.Config
    Logger   *slog.Logger
}

func (c *CaddyManager) EnsureNetwork(ctx context.Context) error
func (c *CaddyManager) Start(ctx context.Context) error
func (c *CaddyManager) Stop(ctx context.Context) error
func (c *CaddyManager) Status(ctx context.Context) (*CaddyStatus, error)
func (c *CaddyManager) IsRunning(ctx context.Context) (bool, error)
```

### 8. Integration with deployer

Modify `deployer.Deploy()` to call `CaddyManager.EnsureNetwork()` before running `docker compose up` for any app. This guarantees the `caddy` network exists. The app's compose override already adds the `caddy` network and labels (from wu-05).

### 9. Config additions

Add to the `Server` config struct:
- `acme_email` (string, optional) — email for Let's Encrypt. Defaults to `webmaster@<deploy_domain>`.
- The existing `deploy_domain` is used for herald's own Caddy routing.

## Constraints

- `go build ./...` must pass.
- `go test ./...` must pass.
- Shell out to `docker compose` and `docker network` — do not use the Docker SDK.
- Do not modify Caddy's internal configuration directly — rely entirely on Docker labels for routing.
- The Caddy data volume (`caddy_data`) must persist across restarts to avoid re-requesting certificates.
- Do not handle Caddy's internal TLS configuration — caddy-docker-proxy handles ACME automatically.
- Ports 80 and 443 must be free on the host. If they're occupied (e.g., by nginx-proxy), `herald caddy start` will fail with a clear port conflict error.

## Failure Modes

- **Port 80/443 already in use**: `docker compose up` fails. Detection: check error output for "address already in use". Herald should log: `"ports 80/443 are in use. Stop the existing proxy (nginx-proxy?) before starting Caddy."`.
- **Docker socket not mounted**: Caddy can't discover containers. Detection: Caddy starts but no routes are configured. Mitigation: the compose file mounts the socket; if Docker isn't running, compose fails explicitly.
- **Let's Encrypt rate limiting**: Too many cert requests. Mitigation: Caddy handles this internally with backoff. The `caddy_data` volume preserves certs across restarts.
- **herald-proxy-label container adds overhead**: A sleeping Alpine container uses ~1MB RAM. Acceptable for the routing convenience.
