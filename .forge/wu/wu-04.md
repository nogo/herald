# Add webhook HTTP server

## Outcome

Running `herald serve` starts an HTTP server that listens for GitHub webhook POST requests. When a valid webhook arrives (correct HMAC signature, matching repo in config), herald logs the event with repo name, branch, and commit SHA. Invalid signatures are rejected with HTTP 403. Unknown repos (not in config) are rejected with HTTP 404. The server gracefully shuts down on SIGINT/SIGTERM.

## Values

1. Security — HMAC validation is mandatory. No request is processed without a valid signature.
2. Reliability — the server must handle malformed payloads, missing headers, and concurrent requests without panicking.
3. Observability — every webhook request is logged with timestamp, repo, branch, result (accepted/rejected/error).

## Context

- `cmd/serve.go` — stub command that prints "not implemented". This WU replaces it with a real HTTP server.
- `cmd/root.go` — root command. `cmd.Cfg` holds the parsed config (from wu-02). `--data-dir` flag for secrets (from wu-03).
- `internal/config/config.go` — config types. `Config.Server.DeployDomain` is where the webhook listens. `Config.Apps` maps app names to `App` structs with `Repo` and `Branch` fields.
- Herald receives GitHub webhook events. GitHub signs each payload with HMAC-SHA256 using a shared secret. The signature is in the `X-Hub-Signature-256` header.
- The webhook secret is stored in herald's encrypted secrets store under the key `herald/webhook_secret`. It's set via `herald secret set herald/webhook_secret <value>`.
- This WU does NOT trigger deploys — it only validates and logs. wu-05 adds the deploy action.

## Requirements

### 1. HTTP server

Create an HTTP server using Go's `net/http` standard library (no framework). The server listens on `:8080` by default. Add a `--port` flag to `herald serve` (default `8080`).

Routes (use Go 1.22+ `ServeMux` method+path patterns):
- `POST /webhook` — receives GitHub webhook payloads.
- `GET /health` — returns `{"status":"ok"}` with HTTP 200. No auth required.
- All other routes — HTTP 404.

Use `http.NewServeMux()` with method-aware patterns (e.g., `mux.HandleFunc("POST /webhook", handler)` and `mux.HandleFunc("GET /health", handler)`).

### 2. GitHub webhook payload parsing

Parse these GitHub event types (determined by `X-GitHub-Event` header):

**Push event** (`X-GitHub-Event: push`):
```go
type PushPayload struct {
    Ref        string     `json:"ref"`         // "refs/heads/main"
    Before     string     `json:"before"`
    After      string     `json:"after"`       // commit SHA
    Repository Repository `json:"repository"`
    Pusher     Pusher     `json:"pusher"`
}

type Repository struct {
    FullName string `json:"full_name"`  // "nogo/budget-app"
    CloneURL string `json:"clone_url"`
    SSHURL   string `json:"ssh_url"`
}

type Pusher struct {
    Name string `json:"name"`
}
```

**Pull request event** (`X-GitHub-Event: pull_request`):
```go
type PullRequestPayload struct {
    Action      string      `json:"action"`      // "opened", "closed", "synchronize"
    Number      int         `json:"number"`
    PullRequest PullRequest `json:"pull_request"`
    Repository  Repository  `json:"repository"`
}

type PullRequest struct {
    Head   PRRef  `json:"head"`
    Base   PRRef  `json:"base"`
    Merged bool   `json:"merged"`
}

type PRRef struct {
    Ref string `json:"ref"`  // branch name
    SHA string `json:"sha"`
}
```

**Ping event** (`X-GitHub-Event: ping`):
- Respond with HTTP 200 and `{"message":"pong"}`. No further processing. This is sent when a webhook is first registered.

For any other event type, respond with HTTP 200 and `{"message":"event ignored"}`.

### 3. HMAC-SHA256 signature verification

Every request to `/webhook` must be verified:

1. Read the raw request body.
2. Get the `X-Hub-Signature-256` header. Format: `sha256=<hex-encoded-hmac>`.
3. Compute HMAC-SHA256 of the raw body using the webhook secret from the secrets store (`herald/webhook_secret`).
4. Compare using `hmac.Equal` (constant-time comparison).
5. If the header is missing or the signature doesn't match, return HTTP 403 with `{"error":"invalid signature"}`.

The webhook secret is loaded from the secrets store at server startup. If the secret is not found in the store, `herald serve` must exit with an error: `"webhook secret not configured. Run: herald secret set herald/webhook_secret <your-secret>"`.

### 4. Repo matching

After signature verification and payload parsing:

1. Extract the repo full name (e.g., `nogo/budget-app`) from the payload.
2. Extract the branch from `ref` (strip `refs/heads/` prefix for push events).
3. Search `Config.Apps` for entries where `App.Repo` matches the repo AND `App.Branch` matches the branch.
4. A push to `nogo/budget-app:main` may match MULTIPLE apps (budget and tracker both reference that repo+branch). Collect all matches.
5. If no apps match, check if the repo is the server IaC repo itself (for self-update — compare against the repo that `herald init` cloned from). If it matches, log "IaC repo updated" (actual self-update logic is in wu-08).
6. If no apps match at all, return HTTP 200 with `{"message":"no matching apps"}` and log the event.

### 5. Logging

Log every webhook request:
- Timestamp, HTTP method, path, event type, repo, branch.
- Result: "accepted: <app-names>", "rejected: invalid signature", "ignored: no matching apps", "pong".
- Use Go's `log/slog` structured logger.
- In verbose mode, also log the raw payload (but NEVER log the webhook secret or HMAC signature).

### 6. Graceful shutdown

The server must shut down gracefully on SIGINT or SIGTERM:
1. Stop accepting new connections.
2. Wait for in-flight requests to complete (timeout: 10 seconds).
3. Log "herald server stopped" and exit 0.

Use `signal.NotifyContext` and `http.Server.Shutdown`. In Go 1.26, `signal.NotifyContext` sets the cancel cause with signal info — use `context.Cause(ctx)` to log which signal triggered shutdown.

### 7. Accepted webhook response

When a webhook matches one or more apps, respond with HTTP 200 and:
```json
{"message":"accepted","apps":["budget","tracker"]}
```

The actual deploy is triggered asynchronously (in wu-05). The webhook response must return immediately — do not block on deploy execution.

For now (before wu-05), just log the matched apps. The handler should call a `DeployFunc` callback that is initially a no-op logger. wu-05 will replace this with real deploy logic.

```go
type DeployRequest struct {
    AppName  string
    App      config.App
    Repo     string
    Branch   string
    Commit   string
    CloneURL string
}

// In server.go:
type Server struct {
    Config    *config.Config
    Secret    string
    OnDeploy  func(DeployRequest)  // called for each matched app
}
```

## Constraints

- `go build ./...` must pass.
- `go test ./...` must pass.
- Use only Go standard library for HTTP. No Gin, Echo, Chi, etc.
- HMAC validation must use `crypto/hmac` and `crypto/sha256` from the standard library.
- Do not execute any deploy actions — only log matched apps.
- Do not interact with Docker, Caddy, or the filesystem beyond reading the secrets store.
- The server must not block the webhook response on deploy execution (even though deploys aren't implemented yet, the architecture must support async dispatch).

## Failure Modes

- **Webhook secret not set**: Server refuses to start. Detection: error message tells user to run `herald secret set`.
- **Malformed JSON payload**: Return HTTP 400 with `{"error":"invalid payload"}`. Don't panic.
- **Very large payload (DoS)**: Limit request body to 10 MB using `http.MaxBytesReader`.
- **Concurrent webhook requests**: The handler must be goroutine-safe. No shared mutable state beyond the deploy callback.
- **GitHub sends duplicate webhooks**: This is normal (retries on timeout). The handler should be idempotent — logging the same event twice is fine.

## Verification

```bash
go build ./...
go test ./internal/webhook/...

# Manual integration test:
# Terminal 1: start herald with a test config
export HERALD_DATA_DIR=$(mktemp -d)
./herald --data-dir "$HERALD_DATA_DIR" secret set herald/webhook_secret "test-secret"
./herald --data-dir "$HERALD_DATA_DIR" --config testdata/valid.yml serve --port 9999 &

# Terminal 2: send a valid webhook
BODY='{"ref":"refs/heads/main","after":"abc123","repository":{"full_name":"nogo/budget-app","clone_url":"https://github.com/nogo/budget-app.git"},"pusher":{"name":"test"}}'
SIG=$(echo -n "$BODY" | openssl dgst -sha256 -hmac "test-secret" | awk '{print $2}')
curl -X POST http://localhost:9999/webhook \
  -H "Content-Type: application/json" \
  -H "X-GitHub-Event: push" \
  -H "X-Hub-Signature-256: sha256=$SIG" \
  -d "$BODY"
# Should return: {"message":"accepted","apps":["budget","tracker"]}

# Send with wrong signature:
curl -X POST http://localhost:9999/webhook \
  -H "Content-Type: application/json" \
  -H "X-GitHub-Event: push" \
  -H "X-Hub-Signature-256: sha256=wrong" \
  -d "$BODY"
# Should return 403: {"error":"invalid signature"}

# Health check:
curl http://localhost:9999/health
# Should return: {"status":"ok"}

kill %1
rm -rf "$HERALD_DATA_DIR"
```
