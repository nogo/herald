# Add Docker Compose deploy integration

## Outcome

When herald receives a valid webhook for a configured app, it clones (or pulls) the app's git repository, resolves secrets from the encrypted store, writes a compose override file with environment variables and secret references, and runs `docker compose up -d --build`. The app's containers start and are accessible. Running `herald deploy budget` manually triggers the same flow for a named app.

## Values

1. Correctness — a deploy must either fully succeed or leave the previous state untouched. No half-deployed states.
2. Isolation — deploying one app must never affect another app's containers, even if they share the same source repo.
3. Transparency — every deploy step is logged: git pull, compose build, compose up, with durations and exit codes.

## Context

- `internal/webhook/server.go` — webhook server with `OnDeploy func(DeployRequest)` callback. Currently logs but doesn't deploy. This WU provides the real deploy function.
- `internal/config/config.go` — config types. `App` has `Repo`, `Branch`, `Domain`, `EnvFile`, `Compose`, `Override`, `Secrets []SecretRef`.
- `internal/secrets/store.go` — `Resolve(refs []SecretRef)` returns `envVars map[string]string` and `dockerSecrets map[string]string`.
- `cmd/deploy.go` — stub command. This WU makes it trigger a deploy for a named app.
- `cmd/serve.go` — starts the webhook server. This WU wires the deploy function as the `OnDeploy` callback.
- The config's `server.stacks_dir` (e.g., `/opt/deploy`) is the base directory. Each app gets a subdirectory: `/opt/deploy/apps/<app-name>/`.
- Herald shells out to `git` and `docker compose` (not using Docker SDK). This is intentional — compose files may use features not exposed by the SDK, and shelling out matches how users would manually deploy.

## Creates

- `internal/deployer/deployer.go` — deploy logic: git operations, compose operations, secret injection.
- `internal/deployer/deployer_test.go` — unit tests for helper functions (not full integration — no Docker in tests).

## Modifies

- `cmd/deploy.go` — implement `herald deploy <app-name>` using the deployer.
- `cmd/serve.go` — wire `deployer.Deploy` as the `OnDeploy` callback.

## Requirements

### 1. Deploy directory structure

Each app deployment lives in `<stacks_dir>/apps/<app-name>/`:

```
/opt/deploy/apps/
  ├── budget/
  │   ├── repo/              ← git clone of nogo/budget-app
  │   ├── compose.override.yml  ← generated by herald (env, volumes, labels)
  │   └── .env               ← generated from secrets store
  └── tracker/
      ├── repo/              ← separate clone of nogo/budget-app
      ├── compose.override.yml
      └── .env
```

Note: budget and tracker both clone `nogo/budget-app` but into separate directories. Each is an independent deployment.

### 2. Git operations

**First deploy (directory doesn't exist):**
```sh
git clone --branch <branch> --single-branch --depth 1 <clone-url> <app-dir>/repo
```

Use HTTPS clone URL. If a GitHub token is available in the config (`server.github_token`), embed it in the URL: `https://<token>@github.com/nogo/budget-app.git`. This handles private repos.

**Subsequent deploys (directory exists):**
```sh
cd <app-dir>/repo
git fetch origin <branch>
git reset --hard origin/<branch>
```

Use `--depth 1` on clone to minimize disk usage. The fetch+reset pattern ensures we always match the remote exactly, even if someone manually edited files on the server.

### 3. Secret injection

Before running compose, resolve secrets for this app:

1. Call `secrets.Store.Resolve(app.Secrets)` to get `envVars` and `dockerSecrets`.
2. For `envVars`: write them to `<app-dir>/.env` file (Docker Compose auto-loads `.env`). Format: `KEY=value` per line. Overwrite on each deploy.
3. For `dockerSecrets`: write each value to a temp file in `<app-dir>/secrets/<name>`. These will be referenced in the compose override.
4. If the app has an `env_file` configured, it references a file on the server (e.g., `/opt/deploy/envs/.env.budget`). This file is NOT managed by herald — it's manually created. Herald must verify it exists before deploying and error if it doesn't.

### 4. Compose override generation

Generate `<app-dir>/compose.override.yml` that:

1. Adds Caddy Docker labels to the main service (the first service defined in the app's compose file, or a service named `app` or matching the app name). Labels:
   ```yaml
   labels:
     caddy: "<domain>"
     caddy.reverse_proxy: "{{upstreams <port>}}"
   ```
   The port is auto-detected from the compose file's `expose` or `ports` directive. Default to `3000` if not detectable.

2. Connects the service to the `caddy` external network:
   ```yaml
   networks:
     caddy:
       external: true
   ```

3. If the app config has an `override` field (inline YAML), merge it into the override file.

4. If the app config has `env_file`, add it to the service's `env_file` list.

5. If there are Docker secrets, add `secrets` section.

### 5. Docker Compose execution

Run from the `<app-dir>/repo` directory:

```sh
docker compose -f <compose-file> -f <app-dir>/compose.override.yml up -d --build --remove-orphans
```

Where `<compose-file>` is the app's `compose` field (default `compose.yml`), relative to the repo directory.

The compose project name should be `herald-<app-name>` to avoid collisions with manually run compose projects.

Capture stdout and stderr. Log them at info level. If the command exits non-zero, log the error and return an error — do not attempt cleanup (the previous containers may still be running, which is the desired fallback).

### 6. Deploy function signature

```go
type Deployer struct {
    Config    *config.Config
    Secrets   *secrets.Store
    Logger    *slog.Logger
}

func (d *Deployer) Deploy(ctx context.Context, appName string) error
```

This function:
1. Looks up the app in `d.Config.Apps`.
2. Creates the app directory if needed.
3. Clones or pulls the repo.
4. Resolves secrets.
5. Generates the compose override.
6. Runs `docker compose up -d --build`.
7. Returns nil on success, error on failure.

### 7. Manual deploy command

`herald deploy <app-name>`:
1. Loads config.
2. Validates that `<app-name>` exists in `config.Apps`.
3. Calls `Deployer.Deploy(ctx, appName)`.
4. Prints success or error message.
5. Exits with code 0 on success, 1 on failure.

`herald deploy` with no arguments prints the list of available app names.

### 8. Webhook integration

In `cmd/serve.go`, create a `Deployer` instance and wire `Deploy` as the webhook server's `OnDeploy` callback. Deploys triggered by webhooks run in a goroutine (non-blocking). Only one deploy per app should run at a time — use a per-app mutex. If a deploy is already in progress for an app and another webhook arrives, queue it (run after current finishes) but don't queue more than one.

### 9. Deploy locking

Use a `sync.Map` of per-app `sync.Mutex` locks. Before deploying an app, acquire its lock. This prevents concurrent deploys of the same app (e.g., rapid pushes). Different apps can deploy concurrently.

**Go 1.26 idioms**: Use `sync.WaitGroup.Go(func() {...})` (Go 1.25+) when spawning deploy goroutines from the webhook handler instead of manual `wg.Add(1)`/`defer wg.Done()`. Use `os.OpenRoot` (Go 1.24+) to scope file writes (`.env`, `compose.override.yml`) to the app deployment directory for security. Use `strings.Lines()` for iterating over multi-line command output.

## Constraints

- `go build ./...` must pass.
- `go test ./...` must pass.
- Shell out to `git` and `docker compose` — do not use the Docker SDK or a git library.
- Use `os/exec` for all subprocess execution.
- Set a 10-minute timeout on deploy operations (`context.WithTimeout`).
- Never log secret values. Log secret key names only.
- Do not manage Caddy's lifecycle — just add labels to containers. wu-06 handles Caddy.
- Do not manage GitHub webhooks — wu-07 handles that.

## Failure Modes

- **Git clone fails (network, auth)**: Return error with the git stderr output. Previous state (if any) is untouched.
- **Docker compose build fails**: Return error with compose stderr. Previous containers keep running.
- **Missing env_file**: Return error before running compose: `"env_file '/opt/deploy/envs/.env.budget' not found"`.
- **Secret not found in store**: Return error: `"secret 'budget/db_password' not found"`. Don't deploy.
- **Compose override merge conflict**: The inline override YAML must be valid. If it's malformed, return a parse error.
- **Docker socket not accessible**: `docker compose` fails with permission error. Herald must be in the `docker` group or run as root.
- **Concurrent deploys of same app**: Per-app mutex prevents this. Second deploy waits.
