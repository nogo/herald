# Add stack update command

## Outcome

Running `herald update nextcloud` executes the update script defined in the stack's config, performing a scripted multi-step update (e.g., pull new images, rebuild, run migrations, verify). The user no longer needs to remember or type individual update steps. Running `herald update --list` shows all available stacks and their update scripts. Stacks with `auto_deploy: true` are automatically updated when the server IaC repo is pushed to.

## Values

1. Safety — update scripts must run in a controlled manner. Capture all output. Exit on first error.
2. Transparency — every command in the script is logged with its output and exit code.
3. Recoverability — if an update fails mid-way, the user sees exactly which step failed and can resume manually.

## Context

- `internal/config/config.go` — `Config.Stacks` maps stack names to `Stack` structs: `Path`, `Domain`, `AutoDeploy`, `UpdateScript`.
- `cmd/update.go` — stub command. This WU replaces it.
- The server IaC repo is cloned at `<data_dir>/repo/` (e.g., `/etc/herald/repo/`). Stack paths like `stacks/nextcloud` are relative to this repo root.
- Stack compose files live in the server repo (e.g., `/etc/herald/repo/stacks/nextcloud/compose.yaml`).
- Update scripts are shell scripts in the server repo (e.g., `/etc/herald/repo/stacks/nextcloud/update.sh`).
- Stacks are deployed to `<stacks_dir>/stacks/<stack-name>/` (e.g., `/opt/deploy/stacks/nextcloud/`).
- The Nextcloud compose file references volumes with bind mounts to `/srv/nextcloud/` — these paths are absolute and don't change.
- `internal/deployer/deployer.go` — contains the git clone/pull and compose up logic. Stacks use similar patterns but with some differences (no git clone from external repo, compose files are in the IaC repo).

## Creates

- `internal/stacks/manager.go` — stack management: setup, update, status.
- `internal/stacks/manager_test.go` — unit tests.

## Modifies

- `cmd/update.go` — implement `herald update <stack>` and `herald update --list`.
- `internal/webhook/server.go` — when a push to the IaC repo is received, trigger updates for stacks with `auto_deploy: true`.

## Requirements

### 1. Stack setup

Before a stack can be updated, it needs to be set up. Stack setup:

1. Copy (or symlink) the stack directory from the IaC repo to the stacks deployment dir:
   ```
   /etc/herald/repo/stacks/nextcloud/ → /opt/deploy/stacks/nextcloud/
   ```
   Use symlinks so that pulling the IaC repo automatically updates the compose files.

2. Ensure the `caddy` network exists.

3. Generate a compose override with Caddy labels for the stack's domain (same pattern as app deploys in wu-05).

4. If the stack's compose file references secrets from the herald secrets store, resolve them.

### 2. Update command

`herald update <stack-name>`:

1. Validate that `<stack-name>` exists in `config.Stacks`.
2. Pull the latest IaC repo (`git pull` in `<data_dir>/repo/`).
3. Check that the update script exists at the configured path.
4. Set up the stack if not already set up.
5. Execute the update script.
6. Print the result (success/failure, duration).

`herald update --list`:
```
Available stacks:
  nextcloud    cloud.example.com          auto:no    stacks/nextcloud/update.sh
  ghost        blog.example.com  auto:no    stacks/ghost/update.sh
```

### 3. Update script execution

The update script is executed with:
- Working directory: the stack's deployment directory (e.g., `/opt/deploy/stacks/nextcloud/`).
- Environment: inherits herald's environment plus:
  - `STACK_NAME` — the stack name from config
  - `STACK_DIR` — absolute path to the stack deployment directory
  - `STACK_DOMAIN` — the stack's domain
  - `COMPOSE_FILE` — path to the stack's compose file
- Shell: `/bin/bash -euo pipefail` (fail on first error, fail on undefined vars, fail on pipe errors).
- Stdout and stderr are captured and logged in real-time (streamed to herald's log, not buffered).
- Timeout: 30 minutes (configurable via a flag `--timeout`).

```go
func (m *StackManager) RunUpdateScript(ctx context.Context, stackName string) error
```

### 4. Example update scripts

The WU should create example update scripts in a testdata directory to validate the execution model. These are reference implementations — the real scripts will be written by the user in their server repo.

**Example: Nextcloud update (`stacks/nextcloud/update.sh`)**:
```bash
#!/bin/bash
set -euo pipefail

echo "=== Nextcloud Update ==="
echo "Stack: $STACK_NAME"
echo "Dir:   $STACK_DIR"

# Enable maintenance mode
docker compose -f "$COMPOSE_FILE" exec -T nextcloud-app php occ maintenance:mode --on

# Pull latest images and rebuild
docker compose -f "$COMPOSE_FILE" build --pull
docker compose -f "$COMPOSE_FILE" up -d

# Wait for containers to be healthy
sleep 10

# Run upgrade
docker compose -f "$COMPOSE_FILE" exec -T nextcloud-app php occ upgrade
docker compose -f "$COMPOSE_FILE" exec -T nextcloud-app php occ db:add-missing-indices
docker compose -f "$COMPOSE_FILE" exec -T nextcloud-app php occ db:add-missing-columns

# Disable maintenance mode
docker compose -f "$COMPOSE_FILE" exec -T nextcloud-app php occ maintenance:mode --off

echo "=== Nextcloud Update Complete ==="
```

### 5. Auto-deploy on IaC repo push

When the webhook server receives a push event for the server's IaC repo:

1. Pull the latest IaC repo.
2. Reload the config.
3. For each stack with `auto_deploy: true`:
   - Run the compose up command (but NOT the update script — auto-deploy just does `docker compose up -d --build`, not the full update procedure).
4. For stacks with `auto_deploy: false`: log that the IaC repo was updated but no auto-deploy is configured.

This allows you to push compose file changes (e.g., bump an image version) and have them applied automatically for opt-in stacks, while sensitive stacks like Nextcloud require manual `herald update`.

### 7. Script safety

- Update scripts run as the same user as herald (not root, unless herald runs as root).
- Scripts have access to Docker (via `docker compose exec`) because the user is in the `docker` group.
- If the script exits non-zero, `Update()` returns an error with the exit code and last 50 lines of output.
- Herald does not retry failed updates — the user investigates and re-runs manually.

## Constraints

- `go build ./...` must pass.
- `go test ./...` must pass.
- Shell out to `bash` for script execution. Do not try to parse or interpret the script in Go.
- Stream script output in real-time — don't buffer until completion.
- Do not modify the update scripts — they are user-authored content in the server repo.
- Do not run `docker compose down` before updates — that would cause downtime. Let the update script decide the update strategy.
- The compose override for Caddy labels must not conflict with the stack's own compose file.

## Failure Modes

- **Update script doesn't exist**: Error: `"update script 'stacks/nextcloud/update.sh' not found in server repo"`.
- **Update script not executable**: Herald should `chmod +x` the script before running, or invoke it as `bash <script>`.
- **Maintenance mode left on after failure**: If the Nextcloud update script fails between maintenance-on and maintenance-off, Nextcloud stays in maintenance mode. This is the script's responsibility — herald can't know how to recover. The user sees the script output and can manually disable maintenance mode.
- **IaC repo pull fails**: Network error. Log and skip auto-updates for this push event.
- **Stack compose file has syntax error**: `docker compose up` fails. Log the error, don't affect other stacks.
