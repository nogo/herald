# Add preview deployments

## Outcome

When a pull request is opened or a feature branch is pushed for an app with `preview.enabled: true`, herald deploys the branch to a dynamic subdomain (e.g., `checkout-redesign.preview.basalt.solutions`). When the PR is closed or the branch is deleted, herald tears down the preview deployment and removes the domain. Running `herald preview list` shows all active preview deployments with their URLs.

## Values

1. Automatic lifecycle — previews are created and destroyed automatically. No manual intervention.
2. Isolation — each preview is a fully independent deployment with its own containers, network namespace, and domain.
3. Clean teardown — no orphaned containers, volumes, or Caddy routes after a preview is removed.

## Context

- `internal/config/config.go` — `App.Preview` is `*PreviewConfig` with `Enabled bool` and `Domain string` (wildcard pattern like `*.preview.basalt.solutions`).
- `internal/webhook/server.go` — receives GitHub push and pull_request events. `PushPayload` has `Ref` (branch). `PullRequestPayload` has `Action` ("opened", "closed", "synchronize"), `Number`, `PullRequest.Head.Ref` (branch name), `PullRequest.Merged`.
- `internal/deployer/deployer.go` — `Deploy()` handles cloning, building, and composing up. Preview deploys need a variant that uses a different directory, domain, and project name.
- `internal/caddy/caddy.go` — Caddy auto-discovers containers via Docker labels. Preview containers get labels with the preview subdomain.
- `cmd/preview.go` — stub command. This WU replaces it.
- Caddy's automatic TLS works for subdomains if the wildcard domain's DNS has a wildcard A record pointing to the server. Let's Encrypt can issue individual certs per subdomain (HTTP-01 challenge) without needing a wildcard cert — each preview subdomain gets its own cert automatically.

## Creates

- `internal/preview/manager.go` — preview deployment lifecycle management.
- `internal/preview/manager_test.go` — unit tests.
- `internal/preview/state.go` — tracks active previews in a JSON file on disk.

## Modifies

- `cmd/preview.go` — implement `herald preview list` and `herald preview remove <id>`.
- `internal/webhook/server.go` — add preview deploy/teardown logic for push and pull_request events.

## Requirements

### 1. Preview subdomain derivation

From a branch name, derive the preview subdomain:

```go
func SubdomainFromBranch(branch string, previewDomain string) string
```

Rules:
- Strip `refs/heads/` prefix if present.
- Replace `/` with `-` (e.g., `feature/checkout` → `feature-checkout`).
- Replace any non-alphanumeric characters (except `-`) with `-`.
- Lowercase everything via `strings.ToLower`.
- Truncate to 63 characters (DNS label limit).
- Remove leading/trailing hyphens.

**Go 1.26 idiom**: Use `strings.SplitSeq` and iterator patterns for branch name parsing where appropriate.
- Insert into the wildcard domain: `*.preview.basalt.solutions` → `feature-checkout.preview.basalt.solutions`.

Examples:
- `feature/checkout-redesign` → `feature-checkout-redesign.preview.basalt.solutions`
- `fix/bug-123` → `fix-bug-123.preview.basalt.solutions`
- `main` → should NOT create a preview (main branch deploys to production domain).

### 2. Preview state file

Active previews are tracked in `<data_dir>/previews.json`:

```json
{
  "previews": [
    {
      "id": "basalt-app-feature-checkout",
      "app_name": "basalt-app",
      "branch": "feature/checkout",
      "domain": "feature-checkout.preview.basalt.solutions",
      "directory": "/opt/deploy/previews/basalt-app-feature-checkout",
      "compose_project": "herald-preview-basalt-app-feature-checkout",
      "created_at": "2026-03-14T10:00:00Z",
      "commit": "abc123"
    }
  ]
}
```

This file is NOT encrypted — it contains no secrets. It's used to track what's running so herald can clean up.

### 3. Preview deploy flow

When a webhook arrives that matches a preview-enabled app on a non-default branch:

1. Derive the preview subdomain from the branch name.
2. Generate a preview ID: `<app-name>-<sanitized-branch>`.
3. Check if a preview with this ID already exists in the state file.
4. If exists: update (git pull, rebuild, compose up).
5. If new: create:
   a. Create directory: `<stacks_dir>/previews/<preview-id>/`.
   b. Clone the repo at the specified branch.
   c. Resolve secrets (same as production deploy — previews share the app's secrets).
   d. Generate compose override with:
      - Caddy labels pointing to the preview subdomain.
      - Modified compose project name to avoid collisions.
      - Any app-specific overrides from config.
   e. Run `docker compose up -d --build`.
   f. Add entry to `previews.json`.
6. Log: `preview deployed: feature-checkout.preview.basalt.solutions`.

### 4. Preview teardown flow

When a PR is closed (merged or not) or a branch is deleted:

1. Identify the preview by app name + branch.
2. Run `docker compose down --volumes --remove-orphans` in the preview directory.
3. Remove the preview directory.
4. Remove the entry from `previews.json`.
5. Log: `preview removed: feature-checkout.preview.basalt.solutions`.

Caddy automatically stops routing to the domain when the containers are removed (no labels = no route).

### 5. Webhook event handling for previews

**Push event** (`X-GitHub-Event: push`):
- If the branch is the app's configured default branch (e.g., `main`): this is a production deploy (handled by existing wu-05 logic). Do NOT create a preview.
- If the branch is any other branch AND the app has `preview.enabled: true`: create or update a preview.
- If the push is a branch deletion (`deleted: true` in payload, `after` is all zeros): tear down the preview.

**Pull request event** (`X-GitHub-Event: pull_request`):
- `action: "opened"` or `action: "synchronize"` (new commits pushed to PR): create or update preview using the PR's head branch.
- `action: "closed"`: tear down the preview for the PR's head branch.

### 6. CLI commands

**`herald preview list`**:
```
Active previews:
  ID                                    Domain                                      App           Branch                Created
  basalt-app-feature-checkout           feature-checkout.preview.basalt.solutions    basalt-app    feature/checkout      2h ago
  basalt-app-fix-bug-123                fix-bug-123.preview.basalt.solutions         basalt-app    fix/bug-123           30m ago
```

If no previews are active: `No active previews.`

**`herald preview remove <id>`**:
- Tears down the specified preview.
- Prints: `preview 'basalt-app-feature-checkout' removed`.

**`herald preview cleanup`**:
- Finds and removes previews whose branches no longer exist on the remote (stale previews).
- For each preview, runs `git ls-remote --heads <repo> <branch>` to check if the branch exists.
- Removes previews for deleted branches.
- Prints summary of removed previews.

### 8. DNS requirement

Preview subdomains require a wildcard DNS record. This is NOT managed by herald — it's a manual DNS setup. The completion message from `herald init` (wu-08) should note: `"For preview deploys, add a wildcard DNS record: *.preview.basalt.solutions → <server-ip>"`.

Document this in the help text for `herald preview`.

## Constraints

- `go build ./...` must pass.
- `go test ./...` must pass.
- Preview containers must use a unique compose project name to avoid collisions with production or other previews.
- Preview containers must join the `caddy` network for automatic TLS.
- Do not manage DNS — only Docker containers and Caddy labels.
- Preview state file (`previews.json`) must be written atomically (temp file + rename).
- Limit the number of concurrent previews per app to 10 (configurable). If exceeded, reject new previews with an error.
- Clean up Docker images from old previews during teardown: `docker image prune -f --filter label=com.herald.preview=<id>`.

## Failure Modes

- **Wildcard DNS not configured**: Preview deploys succeed (containers run, Caddy gets labels) but the domain doesn't resolve. Herald can't detect this — it's a DNS issue. Document the requirement.
- **Branch name collision**: Two branches with names that sanitize to the same subdomain (unlikely but possible). Mitigation: use the full sanitized name including app prefix as the preview ID.
- **Orphaned previews**: Branch deleted on GitHub but webhook fails to deliver (network issue). Mitigation: `herald preview cleanup` checks remote branches.
- **Disk space**: Many active previews consume disk (cloned repos + Docker images). Mitigation: `--depth 1` clones + image pruning on teardown.
- **Secrets shared with production**: Preview deploys use the same secrets as production. This may be undesirable for database URLs etc. Mitigation: document that users should configure separate env files for preview if needed (future enhancement).
