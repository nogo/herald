# Add sync and status commands

## Outcome

Running `herald status` shows a comprehensive overview of all services: apps, stacks, and previews — with their running state, domain, container health, and last deploy time. Running `herald sync` reconciles the config with reality: deploys apps that should be running but aren't, removes containers for apps no longer in config, updates Caddy labels, and re-registers GitHub webhooks. The status command is the go-to "what's happening on this server" view.

## Values

1. Accuracy — status must reflect actual Docker state, not cached or assumed state. Query Docker on every call.
2. Actionable output — if something is wrong (container crashed, domain unreachable, webhook missing), status should surface it clearly.
3. Non-destructive reads — `herald status` never modifies anything. Only `herald sync` makes changes.

## Context

- `internal/config/config.go` — `Config.Apps` and `Config.Stacks` define what should be running.
- `internal/deployer/deployer.go` — `Deployer.Deploy()` deploys an app.
- `internal/stacks/manager.go` — `StackManager.Setup()` and `ComposeUp()` manage stacks.
- `internal/caddy/caddy.go` — `CaddyManager.IsRunning()` and `Status()` check Caddy.
- `internal/github/webhooks.go` — `SyncWebhooks()` manages GitHub webhooks.
- `internal/preview/manager.go` — `PreviewManager.List()` lists active previews.
- `cmd/status.go` — currently prints a simple config summary (from wu-02). This WU replaces it with a live Docker status view.
- `cmd/sync.go` — stub command. This WU replaces it.
- Herald uses compose project names like `herald-<app-name>` for apps and `herald-preview-<id>` for previews.

## Creates

- `internal/status/collector.go` — collects status from Docker, config, and previews.
- `internal/status/collector_test.go` — unit tests.

## Modifies

- `cmd/status.go` — full status display with live Docker data.
- `cmd/sync.go` — reconciliation logic.

### 2. Status data collection

```go
type StatusCollector struct {
    Config    *config.Config
    DataDir   string
    Logger    *slog.Logger
}

type ServerStatus struct {
    ServerName    string
    Caddy         CaddyStatus
    Apps          []AppStatus
    Stacks        []StackStatus
    Previews      []PreviewStatus
    Webhooks      []WebhookStatus
}

type AppStatus struct {
    Name            string
    Domain          string
    Branch          string
    State           string    // "running", "stopped", "not deployed", "error"
    ContainersUp    int
    ContainersTotal int
    LastCommit      string    // short SHA
}

type StackStatus struct {
    Name            string
    Domain          string
    State           string
    ContainersUp    int
    ContainersTotal int
}

func (c *StatusCollector) Collect(ctx context.Context) (*ServerStatus, error)
```

### 3. Docker state inspection

For each app/stack, query Docker for container status:

```sh
docker compose -p herald-<name> ps --format json
```

This returns JSON with container names, state (running/exited/restarting), health status, and ports. Parse the JSON output to determine:
- How many containers are defined (total)
- How many are running (up)
- Overall state: all running = "running", some running = "degraded", none running = "stopped"

For apps that have never been deployed (no directory exists at `<stacks_dir>/apps/<name>/`), report "not deployed".

### 4. Last commit detection

For deployed apps, read the current HEAD commit from the cloned repo:

```sh
git -C <app-dir>/repo rev-parse --short HEAD
```

Display this in the status output so users can see which commit is deployed.

### 5. Webhook status

For each unique repo in the config, check if a webhook is registered by reading the state from the last `herald webhooks sync` run. Store webhook registration state in `<data_dir>/webhooks.json`:

```json
{
  "nogo/budget-app": {"id": 12345, "registered": true},
  "nogo/sidenote": {"id": 12346, "registered": true}
}
```

This file is updated by `herald webhooks sync` (wu-07). The status command reads it to show webhook state without hitting the GitHub API on every status check.

If the file doesn't exist, show "unknown" for webhook status.

### 6. Sync command

`herald sync` reconciles desired state (config) with actual state (Docker):

```go
func Sync(ctx context.Context, config *config.Config, deployer *deployer.Deployer, 
    stacks *stacks.StackManager, caddy *caddy.CaddyManager, 
    github *github.GitHubClient, secrets *secrets.Store) error
```

Steps:
1. **Pull IaC repo**: `git pull` in `<data_dir>/repo/`.
2. **Reload config**: Re-parse the config file (it may have changed).
3. **Ensure Caddy is running**: If not, start it.
4. **Sync webhooks**: Call `SyncWebhooks()` (register missing, remove stale).
5. **For each app in config**:
   - If not deployed: clone the repo (but don't deploy — user should run `herald deploy`).
   - If deployed but stopped: log a warning. Don't auto-restart (may have been intentionally stopped).
   - If deployed and running: check if the deployed commit matches the remote HEAD. If not, log "app has pending updates".
6. **For each stack in config**:
   - If not set up: set up (symlink, override file).
   - If set up and running: log OK.
   - If set up and stopped: log warning.
7. **Orphan detection**: Find compose projects with `herald-` prefix that don't match any app or stack in the config. Log them as orphans: `"orphan detected: herald-old-app (not in config)"`.

Print a summary:
```
Sync complete:
  Config reloaded
  Caddy: running
  Webhooks: 3 synced, 1 created, 0 removed
  Apps: 4 configured, 3 deployed, 1 not deployed
  Stacks: 2 configured, 2 running
  Orphans: 0
  
Pending actions:
  → Run 'herald deploy sidenote' to deploy (not yet deployed)
  → App 'budget' has new commits (deployed: abc1234, remote: def5678)
```

### 7. Output formatting

Use a simple text-based table format. No colors or unicode beyond basic box-drawing characters (keep it terminal-friendly and pipeable). Use `●` for running, `○` for stopped, `✗` for errors.

### 8. JSON output flag

Add `--json` flag to `herald status`. When set, output the full `ServerStatus` struct as JSON instead of the formatted table. Useful for scripting and monitoring integrations. Use `omitzero` JSON tags (Go 1.24+) on status struct fields so zero-valued fields (empty strings, zero ints) are omitted from JSON output for cleaner output.

## Constraints

- `go build ./...` must pass.
- `go test ./...` must pass.
- `herald status` must NEVER modify state. Read-only.
- `herald sync` must not auto-deploy apps that have never been deployed. Only log that they need deployment.
- `herald sync` must not auto-restart stopped containers. Only log warnings.
- Shell out to `docker compose ps` and `git` for state inspection.
- Status collection should complete within 10 seconds even with many services.
- Do not call the GitHub API from `herald status` — use the cached `webhooks.json` file.

## Failure Modes

- **Docker not running**: `docker compose ps` fails. Status should catch this and report: `"Docker is not accessible"` instead of crashing.
- **Stale webhooks.json**: Webhook state shown may be outdated. Mitigation: show "last synced: <timestamp>" in the webhooks section.
- **Large number of containers**: `docker compose ps` for many projects could be slow. Mitigation: run queries concurrently using `sync.WaitGroup.Go()` (Go 1.25+) — one goroutine per app/stack.
- **Config file changed but not synced**: Status shows config state, Docker shows runtime state. They may disagree. This is expected — `herald sync` fixes it.

```bash
go test ./internal/status/...

```
