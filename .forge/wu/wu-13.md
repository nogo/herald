# Add web status page to herald serve

## Outcome

When `herald serve` is running, visiting `https://deploy.example.com/` in a browser shows a live status page displaying all apps, stacks, and previews with their running state, domains, container health, and last deploy info. The page auto-refreshes. It requires no database — all data is collected live from Docker on each page load. The page is protected by basic authentication.

## Values

1. Zero infrastructure — the status page is part of `herald serve`. No separate process, no database, no SPA build step.
2. Live data — every page load queries Docker for current state. What you see is what's running.
3. Security — the page is behind basic auth. No public access to infrastructure details.

## Context

- `internal/webhook/server.go` — HTTP server that handles `POST /webhook` and `GET /health`. This WU adds HTML routes to the same server.
- `internal/status/collector.go` (wu-11) — `StatusCollector.Collect()` returns `*ServerStatus` with apps, stacks, previews, webhooks, Caddy state. This is the data source for the status page.
- `internal/config/config.go` — `Config.Server.DeployDomain` is where the status page is served.
- `internal/secrets/store.go` — the status page password is stored at `herald/status_password` in the encrypted secrets store.
- The status page must work without JavaScript for the initial render. An optional auto-refresh meta tag or minimal JS for live updates is acceptable.
- Go 1.26's `http.CrossOriginProtection` should wrap the status page routes for CSRF protection.
- Use Go's `html/template` for rendering — no frontend framework, no build step, no node_modules.

## Creates

- `internal/web/handler.go` — HTTP handlers for the status page.
- `internal/web/handler_test.go` — unit tests.
- `internal/web/templates/` — directory with Go HTML templates.
- `internal/web/templates/layout.html` — base layout (head, nav, footer).
- `internal/web/templates/status.html` — main status dashboard.
- `internal/web/templates/app.html` — single app detail view.
- `internal/web/static/style.css` — minimal CSS (embedded via `embed.FS`).

## Modifies

- `internal/webhook/server.go` — add status page routes to the existing HTTP server.
- `cmd/serve.go` — wire the status page handler.

## Requirements

### 1. Routes

Add these routes to the existing `herald serve` HTTP server:

```
GET /                → status dashboard (HTML)
GET /app/{name}      → app detail page (HTML)
GET /api/status      → JSON API (same as herald status --json)
POST /webhook        → (existing) GitHub webhook handler
GET /health          → (existing) health check
```

Use Go 1.22+ `ServeMux` method+path patterns.

### 2. Authentication

The status page requires HTTP Basic Auth:
- Username: `herald` (hardcoded).
- Password: stored in the secrets store at `herald/status_password`.
- If `herald/status_password` is not set, the status page is disabled. Serve a message: `"Status page not configured. Run: herald secret set herald/status_password <your-password>"`.

Implement as middleware that wraps only the status page routes (not `/webhook` or `/health`).

The `/api/status` endpoint also requires Basic Auth — it returns the same data as the HTML page but as JSON.

### 4. App detail page (`/app/{name}`)

Shows detailed info for a single app:
- Domain (linked)
- Repo + branch + current commit SHA
- Container list with individual status, health, uptime
- Recent deploy output (last 50 lines of compose up output, if stored)
- Config summary (env_file, secrets referenced, override preview — no secret values)
- Link to GitHub repo

### 5. Templates and embedding

Use Go's `embed.FS` to embed templates and static files into the binary:

```go
//go:embed templates/*.html static/*
var content embed.FS
```

Templates use `html/template` with a shared layout:
- `layout.html` — defines `<html>`, `<head>` (with CSS link), `<body>` wrapper, nav bar.
- `status.html` — extends layout, renders the dashboard.
- `app.html` — extends layout, renders app detail.

### 6. CSS

Minimal, clean CSS in `static/style.css`. No framework (no Tailwind, no Bootstrap). Requirements:
- System font stack (`-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif`).
- Dark/light mode via `prefers-color-scheme` media query.
- Tables with alternating row colors.
- Status indicators as colored dots (CSS `::before` pseudo-element or inline SVG).
- Max-width container (800px) centered on page.
- Mobile-friendly (tables scroll horizontally on small screens).

### 7. JSON API (`/api/status`)

Returns the same `ServerStatus` struct from wu-11 as JSON. This enables:
- Custom monitoring integrations
- External dashboards
- Scripting (`curl -u herald:pass https://deploy.example.com/api/status | jq .`)

Content-Type: `application/json`. Uses the same Basic Auth as the HTML pages.

### 8. Data collection caching

To avoid hammering Docker on every page load (especially with auto-refresh), cache the `ServerStatus` for 5 seconds:

```go
type cachedStatus struct {
    mu      sync.Mutex
    status  *status.ServerStatus
    fetched time.Time
    ttl     time.Duration
}

func (c *cachedStatus) Get(ctx context.Context, collector *status.StatusCollector) (*status.ServerStatus, error)
```

If the cached data is less than 5 seconds old, return it. Otherwise, re-collect from Docker.

### 9. Web handler struct

```go
type WebHandler struct {
    Collector  *status.StatusCollector
    Config     *config.Config
    Templates  *template.Template
    Password   string  // from secrets store
    Logger     *slog.Logger
    cache      cachedStatus
}

func NewWebHandler(collector *status.StatusCollector, config *config.Config, password string, logger *slog.Logger) *WebHandler
func (h *WebHandler) RegisterRoutes(mux *http.ServeMux)
```

### 10. Integration with webhook server

In `internal/webhook/server.go`, the `Server` struct gains a `WebHandler` field. When creating the `ServeMux`:

```go
mux := http.NewServeMux()
mux.HandleFunc("POST /webhook", s.handleWebhook)
mux.HandleFunc("GET /health", s.handleHealth)

if s.Web != nil {
    s.Web.RegisterRoutes(mux)  // adds GET /, GET /app/{name}, GET /api/status
}
```

The web handler is only initialized if `herald/status_password` is set in the secrets store.

## Constraints

- `go build ./...` must pass.
- `go test ./...` must pass.
- No JavaScript frameworks. No npm/node. No build step for frontend assets.
- Templates and CSS are embedded in the binary via `embed.FS`.
- No database. All data is live from Docker + config.
- The status page must not slow down webhook processing. Status collection runs in its own goroutine with caching.
- Secret values must NEVER appear on the status page. Only show secret key names.
- Use `html/template` (not `text/template`) for auto-escaping of HTML output.
- Use `http.CrossOriginProtection` (Go 1.25+) to wrap the status page mux for CSRF protection.
- The status page must work behind Caddy's reverse proxy (respect `X-Forwarded-*` headers for link generation).

## Failure Modes

- **Status password not set**: Status page is disabled. `/` returns a helpful message. Webhook and health endpoints still work.
- **Docker not accessible**: Status page shows an error banner: `"Cannot connect to Docker"` instead of crashing.
- **Template parsing error**: Caught at startup (templates are parsed in `NewWebHandler`). If templates fail to parse, log the error and disable the status page — don't crash herald.
- **High refresh rate**: Cache prevents Docker spam. Minimum 5-second TTL.
- **Basic Auth over HTTP**: Insecure — credentials sent in cleartext. Mitigation: herald runs behind Caddy with TLS, so the connection is encrypted end-to-end. Log a warning if `deploy_domain` doesn't start with a known domain (suggesting it might not have TLS).
