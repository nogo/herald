# Add secret auto-generation to SecretRef

## Outcome
A `SecretRef` with `generate: base64` (or `alphanumeric` / `hex`) and an optional `length:` causes herald to generate a cryptographically random value and store it on first resolve when the key is absent from the store. Subsequent resolves use the stored value — the generated secret is stable across deploys. Secrets that require human input (`generate` absent) continue to fail with an error when missing. Fresh deployments of infrastructure secrets (db passwords, auth keys) require no manual `herald secret set` calls.

## Values
1. Stable on re-run — generate once, store, reuse. Never overwrite an existing value.
2. Cryptographically random — use `crypto/rand`, not `math/rand`.
3. Applies equally to apps and stacks — generation is in `Store.Resolve()`, shared by both.

## Context
- `internal/config/config.go` — `SecretRef` struct (line 49–53). Add `Generate string`. Validate allowed values in `validate()`.
- `internal/secrets/store.go` — `Resolve()` (line 236) is called by both the deployer (apps) and the stack manager (stacks). Currently returns an error if a key is missing (implicit in the `ok` check at line 247). Extend: if key missing AND `ref.Generate != ""`, generate value → call `s.Set(ref.Key, value)` → use generated value. If key missing AND `ref.Generate == ""`, keep existing error behavior.
- `internal/deployer/deployer.go` and `internal/stacks/manager.go` — both call `Resolve()`. No changes needed in either; generation is transparent to callers.

## Requirements

### 1. Config struct
Add to `SecretRef`:
```go
Generate string `yaml:"generate,omitempty" json:"generate,omitzero"`
Length   int    `yaml:"length,omitempty"   json:"length,omitzero"`
```
`Length` is the number of random bytes used as source entropy. Default: 32 when not set or zero.

### 2. Validation
In `validate()`, for every `SecretRef` across all apps and stacks:
- If `Generate != ""`, it must be one of `"base64"`, `"alphanumeric"`, `"hex"`. Error: `app/stack %q: secrets[%d]: generate must be "base64", "alphanumeric", or "hex", got %q`.
- If `Length != 0`, it must be between 16 and 512 inclusive. Error: `app/stack %q: secrets[%d]: length must be between 16 and 512, got %d`.
- If `Length != 0` and `Generate == ""`: error — `app/stack %q: secrets[%d]: length requires generate to be set`.

### 3. Generation in Resolve()
Extend the missing-key branch in `Resolve()`:

```
if key not in store:
    if ref.Generate == "":
        return error (existing behavior)
    value = generate(ref.Generate)   // see §4
    s.Set(ref.Key, value)            // store immediately, encrypted
    use value
```

`s.Set` acquires the lock internally. `Resolve` reads secrets once at the start (line 238); after a `Set`, re-read is not required — use the generated value directly.

### 4. Generation functions
All use `crypto/rand`. `n` = `ref.Length` if set and > 0, else 32.

- `base64`: `n` random bytes, encoded with `base64.StdEncoding`. Result: `ceil(n*4/3)` characters (padded). Suitable for `BETTER_AUTH_SECRET`, session keys.
- `alphanumeric`: generate `n` output characters from `[a-zA-Z0-9]` (62-char alphabet) using rejection sampling on random bytes. Result: exactly `n` characters. Suitable for database passwords (no special chars that break connection strings).
- `hex`: `n` random bytes, `hex.EncodeToString`. Result: `n*2` lowercase hex characters. Suitable for API keys, HMAC secrets.

### 5. Logging
After generating and storing a secret, log at Info level: `"generated secret"` with key name. Never log the value.

## Constraints
- `go build ./...` must pass.
- Do not modify files outside the Modifies list.
- Never overwrite an existing secret — only generate when the key is absent from the store.
- `crypto/rand` only. No `math/rand`.
- `s.Set()` inside `Resolve()` acquires the file lock. `Resolve()` itself does not hold the lock while calling `Set`. Ensure no deadlock: `readSecrets()` (called at Resolve start, line 238) does NOT hold the lock; only `withLock` calls do.

## Failure Modes
- **crypto/rand failure**: system entropy unavailable. Propagate error from generation up through `Resolve()`. Blast radius: deploy fails. Detection: error message from `crypto/rand`.
- **Set fails after generate**: value generated but not persisted. Return error — do not use the value. Next deploy will regenerate (idempotent intent, though a different value will be generated). Detection: error from `Set`.
- **Concurrent deploys generate different values for the same key**: two deploys race; both see the key missing; both generate. The second `Set` overwrites the first. Services started with the first value will mismatch. Mitigation: `Set` uses `withLock` (file lock), so the writes are serialized. The second goroutine should re-read the key after acquiring the lock — check existence inside the lock before writing. Add this check to `Set`: if key already present, return nil without overwriting (this is a behavior change to `Set` — see below).

**Note**: requirement 5 in this WU changes `Set` semantics: `Set` currently always overwrites. For auto-generation safety, `Resolve` should use a new `SetIfAbsent(key, value string) (used bool, err error)` helper that only writes if the key is not already present. `Set` retains its existing overwrite-always semantics (used by `herald secret set` CLI). `Resolve` uses `SetIfAbsent` for generated secrets.
