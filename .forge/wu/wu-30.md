# Extract shared deploy helpers into deployer

## Outcome

The duplicated deploy helper functions (`buildEnvMap`, `loadConfigFile`, `generateOverride`, `writeEnvFile`, `findComposeFile`) exist once in the `deployer` package. The `services` package's copies are deleted. Tests cover the extracted functions. The `compose` package's `findComposeFile` duplicate is removed.

## Values

1. Single source of truth — each helper exists in exactly one place.
2. Testable — helpers are exported or package-level functions with unit tests.
3. Minimal API change — helpers accept `config.Stack` (from wu-28) and simple parameters, not deployer-specific types.

## Context

- `internal/deployer/deployer.go` — `buildEnvMap` (lines 287-325), `generateOverride` (lines 337-409). These become the canonical implementations, updated to accept `config.Stack`.
- `internal/services/manager.go` — `buildEnvMap` (lines 489-511), `loadConfigFile` (lines 464-486), `generateOverride` (lines 528-577), `writeEnvFile` (lines 514-526), `findComposeFile` (lines 441-448). All deleted.
- `internal/compose/context.go` — `findComposeFile` (lines 180-187). Duplicate of services version. Keep this one (it's in the right package) or move to deployer.
- `internal/preview/manager.go` — `generateOverride` (lines 379-457). Third copy. Will be addressed in wu-37, but this WU must make the deployer version usable by preview.
- `docs/architecture.md` — "Deploy Pipeline" section: pipeline exists once in deployer.

## Requirements

### 1. Extract to helpers.go

Create `internal/deployer/helpers.go` with these exported functions:

```go
// LoadConfigFile parses a KEY=VALUE env file, skipping comments and blank lines.
func LoadConfigFile(path string, logger *slog.Logger) (map[string]string, error)

// BuildEnvMap returns the merged env map: config file base overlaid with resolved secret env vars.
// iacRepoDir is the root of the IaC repo. configFile is the relative path within it.
func BuildEnvMap(configFile, iacRepoDir string, envVars map[string]string, logger *slog.Logger) (map[string]string, error)

// GenerateOverride creates a compose.override.yml for a stack.
// Params struct contains all the varying inputs (domain, deploy dir, default port, project prefix, etc.).
type OverrideParams struct {
    DeployDir     string
    StackName     string
    Domain        string
    ComposeFile   string
    EnvFilePaths  []string            // absolute paths to env files for the override
    DockerSecrets map[string]string
    DefaultPort   string              // "3000" for repo stacks, "80" for path stacks
    InternalNet   string              // e.g. "herald-myapp-internal"
    InlineOverride string             // raw YAML to deep-merge (from stack.Override)
}

func GenerateOverride(params OverrideParams) ([]byte, error)

// WriteEnvFile writes sorted KEY=VALUE pairs to the given path with 0600 permissions.
func WriteEnvFile(path string, envMap map[string]string) error

// WriteDockerSecrets writes each secret value to a file under secretsDir.
func WriteDockerSecrets(secretsDir string, dockerSecrets map[string]string) error
```

### 2. Update deployer.go

`Deploy()` calls the new helpers instead of private methods. Remove the old `buildEnvMap` and `generateOverride` methods from `Deployer`. The `generateOverride` call uses `GenerateOverride` with `OverrideParams{DefaultPort: "3000"}`.

### 3. Update services/manager.go

Remove: `buildEnvMap`, `loadConfigFile`, `generateOverride`, `writeEnvFile`, `findComposeFile`, `validateConfigFilePath`. The `Setup()` and `Update()` methods call the deployer helpers instead. This is a temporary bridge — wu-31 will merge the service logic into deployer entirely.

### 4. Update compose/context.go

Keep `findComposeFile` in `compose` package (it's infrastructure, not domain). Export it as `FindComposeFile`. Remove the duplicate from `services/manager.go`. Update `ResolveService` to use the exported version (it already does internally).

### 5. Tests

Test each helper in `helpers_test.go`:
- `LoadConfigFile`: valid file, comments, blank lines, no `=` lines, missing file.
- `BuildEnvMap`: no config file (pass-through), config + secrets merge, secret overrides config key.
- `GenerateOverride`: basic override with caddy labels, with docker secrets, with inline override merge, with env file paths.
- `WriteEnvFile`: sorted output, 0600 permissions.
- `WriteDockerSecrets`: writes files, 0600 permissions.

### 6. Use DeepMergeYAML consistently

`GenerateOverride` must use `compose.DeepMergeYAML` (not `compose.DeepMerge`) when merging inline overrides. This fixes the existing bug where preview's `generateOverride` uses `DeepMerge` which loses YAML tags like `!override`.

## Constraints

- `mise run check` must pass.
- Do not modify files outside the Modifies/Creates list.
- `GenerateOverride` returns `[]byte` (marshaled YAML). The caller writes it to disk. This keeps the function testable without filesystem.
- Helpers must not depend on `Deployer` or `ServiceManager` struct fields. They take explicit parameters.

## Failure Modes

- **Import cycle**: `services` imports `deployer` for helpers, but `deployer` might import `services`. Detection: `go build ./...` fails with cycle. Mitigation: helpers in deployer have no imports from services.
- **DeepMerge vs DeepMergeYAML**: Using wrong merge function loses `!override` tags. Detection: test that `GenerateOverride` with inline override preserves YAML tags.
- **Signature mismatch**: `services.Setup()` passes different args than `deployer.Deploy()`. Detection: compile error if helper signatures don't accommodate both callers.
